---
'seekstone': patch
---

Symlinks that point outside the vault are now refused. Before, a symlink inside the vault let tools read and write files outside it, and could route a write past `SEEKSTONE_WRITE_PATHS` or into `.seekstone/` and `.trash/`. Now a read or write whose real path is outside the vault fails with an error, unless you set `SEEKSTONE_FOLLOW_SYMLINKS=1` (or `true`). One short exception: a note already in the index stays readable for a moment after its folder is replaced by a symlink, until the file watcher drops it. Dangling symlinks are refused in both modes. Symlinks whose target stays inside the vault work as before. When a link lands inside the vault, `SEEKSTONE_READ_PATHS`, `SEEKSTONE_WRITE_PATHS` and the `.seekstone/` and `.trash/` folders are checked against where it lands, with or without the setting. With the setting on, a link to outside the vault counts as outside any read or write scope you set. The file watcher no longer picks up files through symlinked folders, which the startup index already skipped. A write to a note that is itself a symlink now changes the file it points to and keeps the link; before, it replaced the link with a regular file. A recoverable `delete_note` refuses to run when `.trash` is a symlink out of the vault (without the setting) or to another vault folder. If `.seekstone/history` is reached through such a link at startup, write history is turned off with a warning instead of copying notes there. When `move_note` or `rename_heading` would rewrite links in a note that is now reached through a link, that note is skipped and listed in the result. `undo_write` no longer reports a conflict for a file that still holds its pre-image, such as one a crash left unwritten, and marks it `unchanged`.
